# 海量节点的地区分配与容量调度

目标：不同地区的玩家进入合适节点，同地区也按容量分散；已有房间的好友始终到达同一房间所有者。控制服务实例、玩家账号、客户端大厅入口、房间节点和 P2P 路径是不同对象，不能共用一个“当前节点”字段。

## 分配对象

| 对象 | 选取时机 | 稳定性要求 |
| --- | --- | --- |
| 控制区域/实例 | 启动与控制重连 | 提供统一账号/好友视图，实例切换不导致退出游戏 |
| 大厅/发现入口 | 登录、未进房间时 | 就近、有容量、可访问；不决定所有未来游戏房间的位置 |
| 房间所属节点 | 房主创建房间 | 优先房主实测路径，考虑已知队友和预期人数；创建后绑定 room_id/epoch |
| 访客游戏连接 | 加入已有房间 | 定位已存在的房间所有者，不能各自按地区另选一个节点 |
| P2P 路径 | 房主与访客建立会话后 | 直连优先；失败回退同一房间节点，有真实中继预算 |

示例：广东玩家 A 建房在广州节点，上海好友 B 的大厅入口在上海。B 点击邀请后，中心返回 A 房间的广州入口和固定公钥；B 可与 A 直连，或在广州节点中继。不能因为 B 在上海就返回另一个上海游戏节点。若房主在日本、全部好友在国内，建房时可以评估双方路径后选共同合适的节点；不是单按房主 IP 的国家码作决定。

## 一次分配的流程

1. **确定请求意图与身份。** 区分发现入口、新建房间、加入现有房间、恢复同一会话；重试携带原 allocation_id/幂等键。房间加入先查唯一所有者，不进入新房间的候选算法。
2. **硬过滤。** 节点证书有效、所在池获准、版本/协议匹配、入口实际可达、非 draining/隔离/撤销、心跳新鲜，剩余连接与带宽可供本次用途。用户/组织的地区和信任限制先于分数。
3. **按索引取候选。** 优先地区→相邻地区→明确允许的跨区，结合运营商/ASN、IP 类型和入口能力，从区域索引取少量候选；位置来自受信服务端看到的公网地址，客户端上报和 GeoIP 只作提示，不能凭 IP 推断可达性。
4. **少量真实探测。** 建议返回 5–8 个候选、同时最多 3 个探测，测连接/握手 RTT、失败率、近期抖动。结果绑定短期 probe_id 与有效窗口；不对几万节点同时 ping，不把客户端自报 RTT 当作可信配额。
5. **质量分层并分散。** 先排除显著劣质路径，在相近质量层内按可用容量加权的 Rendezvous 哈希分散用户/房间。哈希键含稳定账号/设备或新房间 ID，权重来自服务端容量，避免所有用户涌向同一个最低 RTT 节点。
6. **原子预留。** 在存储事务中重新检查节点状态、配置版本及余量，创建有期限 reservation；选取失败只在有界候选内重试。筛选时显示“还剩一个位置”不代表并发提交时还能拿到它。
7. **返回签名分配票据。** 绑定账号/会话、用途、节点 ID/固定公钥、入口、房间及 epoch、reservation_id、期限和策略版本。节点验票并确认入场后转为 active allocation，未使用的预留到期释放。

所有步骤归一个 Placement 域实现，HTTP、节点、桥、SDK 不分别维护权重公式。客户端只执行探测、验签和应用分配结果。用户手动选节点也经过相同硬过滤及容量预留，不以“手动”绕过隔离或房间归属。

## 地区、质量与容量权重

起始可配置：同地区优先，但实测路径长期明显更差时允许相邻地区胜出；省市边界不是强制分片。地区未知、同运营商信息不确定时依赖探测，不默认送到北京或第一个节点。

候选成本可由 RTT、RTT 波动/超时率、出口利用率、连接/流量余量、事件循环/转发排队、CPU 压力及跨区成本归一化构成。权重由压测和线上指标调整，不把十个不同单位直接相加。自报机房/带宽只能成为提示；接纳数由控制端额度和观测限制，避免节点夸大容量抢走全部客户端。

可以将同等质量定义为最佳实测 RTT 的固定窗口，例如额外不超过 15–25 ms；这是待测初值，不是全球硬保证。质量明显差的节点不因空闲就加入分散池。容量权重设置上限，单台大服务器也不吸收全区全部新会话。

每节点同时维护硬连接上限、有效带宽预算、预留量和活跃分配。使用保守的账本，例如 `max(中心已确认活跃数, 节点观测活跃数) + 未确认预留数`，避免把同一已确认玩家在中心和节点重复计费，也避免未登记流量造成超配。具体计数单位与现有桥会话/游戏流分别定义，不能直接把 TCP 连接数称为玩家数。

受管池的游戏入口必须验证分配票据，不能保留可绕过配额的旧匿名接纳路径。旧联邦节点单独成池，或为旧流量划定明确的保守预算；迁移期间不能只统计中心分配而忽略旧客户端的实际负载。初始策略建议自有/已验证池优先，完成自动验证的其他节点进入社区池；社区池是否承接默认流量是公开的运维策略，不用入网令牌推断信誉。

建房请求包含可选预期队伍人数；容量不足可换节点或明确拒绝。访客加入已存在房间时，如果所属节点的中继预算不足，不能悄悄换成另一台房间节点。可使用已验证 P2P，但必须如实区分“直连可用”和“保证中继回退余量”；未预留带宽时不得承诺所有玩家同时回退都成功。

## 会话黏性与过载恢复

相近节点负载轻微变化时不迁移已有会话。候选集合按短租期缓存并带策略版本；新分配使用带稳定键的加权哈希，减少列表变化引起的重分配。节点维护窗口先 draining 停收新会话，再等待已有会话排空。

软过载时降低新分配权重，硬过载时停止新增，恢复须连续健康多个窗口并有滞回；不能在 79%/81% 之间反复吸收和抛出玩家。建议起始预留 20% 余量，具体阈值在性能验收后确定。

节点故障时区分：未消费的预留可过期并重选；已建立房间须房主桥重新托管、增加 epoch 并签发新票据，访客随后重连。旧 epoch 的迟到确认/释放不能覆盖新所有者。没有 TCP 复制时，界面明确连接重建。

整地区故障必须限制每秒重新分配量、跨区带宽和重试次数，保留随机延迟及用户优先级。相邻区域也无余量时返回容量不足/排队，不能把故障扩散到全网。控制服务短断但游戏正常时，禁止仅因失去中心心跳就强制搬迁数据面。

## 规模与信息分发

目录按区域、运营商/ASN、能力与池归属索引；客户端仅获取候选、当前分配和房间所有者，不下载全量节点清单。每个节点维持一条主控制长连接和有限的备用入口信息，不与所有节点建连接。区域间同步摘要与相关路由，不复制全世界每秒在线心跳。

热点采用快照只读查询和增量变更；候选缓存有短租期和容量版本，原子预留仍是最后关口。控制区域扩容不等于游戏节点扩容，二者指标分开。跨区好友邀请通过账号会话路由转送，不能让每个节点遍历所有地区搜索好友。

## 必测场景

| 场景 | 必须观察的结果 |
| --- | --- |
| 同地区万人同时启动 | 分散到合格节点；不因单点最低 RTT 形成蜂拥；返回分配的地域与质量可解释 |
| 广东房主、上海访客、海外访客 | 所有访客定位同一房间；可分别选择 P2P，但不会创建三个不同归属 |
| 一个位置被百个请求同时争抢 | 仅一个有效预留；其余重选或拒绝，没有超卖 |
| 同一请求重试、确认包丢失 | 同一分配/预留，不重复占位；到期和释放只作用于对应版本 |
| 节点报假带宽或延迟探测过期 | 不突破中心配额；未知不是 0 ms，不让自报容量垄断分配 |
| 单节点过载、抖动与维护 | 停收新用户，有滞回；已有房间不频繁迁移 |
| 整区故障、邻区也满 | 重连有节流，跨区受预算约束，明确返回容量不足 |
| 10,000 节点目录 | 单客户端探测数和响应体有固定上限，不产生全量广播或平方级连接 |

验收以请求成功率、分配 P99、节点利用率分布、路径质量、错误分配数和故障恢复时长衡量，不只统计平均 RTT 或总 QPS。
