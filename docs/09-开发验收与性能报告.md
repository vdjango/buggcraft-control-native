## 性能方法

机器：AMD EPYC 7K62 云主机，KVM x86-64，4 vCPU，约 3.7 GiB RAM；同机回环 TLS 1.3 `TLS_AES_256_GCM_SHA384`，真实持久 PostgreSQL。该机还有既有服务，不做停服、绑核、调权限或系统调优，结果包含调度噪声。

每模式五轮交错，4 个独立玩家、并发 4；每轮每操作预热 40 请求后测 600。目录包含 10,000 条合成节点行、100,000 条合成会话行，**不是 10,000 台已连接节点或 100,000 个真人长连接**。共 18,000 个正式请求，错误数 0，在线校验和 600/批、候选校验和 4,800/批，候选最多八个。

JSON 对照同一可执行文件：simdjson 自动选择 `haswell`（AVX2）与 `fallback`。OpenSSL 对照仍使用相同 TLS/签名算法，只在服务子进程启动前设置 `OPENSSL_ia32cap=0:0`；实际库报告 `0x400:0x0 env:0:0`，不能称为整个系统完全不用任何 CPU 指令。标准库/操作系统/架构基线保持不变。[OpenSSL 官方开关说明](https://docs.openssl.org/3.4/man3/OPENSSL_ia32cap/)

请求耗时含网络、TLS、签名校验、数据库与调度；资源含服务 CPU/RSS 和测试数据库子进程 CPU。延迟表为五轮各自 P 分位数的中位数，不是把所有样本混合后的分位数；RPS 是固定并发工作负载结果，不是最大容量。

默认自动模式：在线请求服务 CPU 中位约 73.1% 单核、RSS 最大约 15.5 MiB，数据库每批 CPU 中位 0.39 秒；候选请求约 76.1% 单核、RSS 最大约 16.3 MiB，数据库每批 CPU 中位 1.40 秒。RSS 只代表这个负载和连接数，不外推十万连接。

小请求端到端差异落在噪声/系统开销范围，未证明 SIMD 或密码硬件开关有稳定可感知收益；因此保留库默认安全硬件分派，不以个别“关闭后更快”的测量更改密码策略。该负载主要开销仍在数据库、签名、网络与调度，后续优先按剖析优化，而不是硬加 AVX512。

## 本次解决的实际瓶颈

压测发现地区候选池过滤未充分命中复合索引：执行计划约 34,279 次共享缓冲命中、约 103.8 ms SQL 执行，最初同账号并发样本约 9.7 RPS。将池归属变成索引等值条件、补充 `(pool,region,shard,id)` 活节点索引，保留分桶轮转与有界候选后，该阶段单账号样本约 205 RPS。

之后改为独立玩家负载，启用控制小包 TCP_NODELAY，五轮结果如上。初期样本没有完成同口径五轮，而且账号/网络配置也变了，**不把 9.7→783 称作纯索引或 SIMD 的倍数收益**。TCP_NODELAY 后实测尾延迟明显改善，但同样不把多个阶段叠加归因于一种优化。

候选不会固定只看全网前八台：按地区/池/分桶索引轮转、ID 游标取有界窗口，再以稳定键容量加权分散。最终容量仍在事务重检，不依赖候选快照或客户端自报 RTT。
