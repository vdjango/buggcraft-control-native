## 旧系统迁移

保留原联邦独立模式，新增受管接入适配，不强制所有已安装节点立即换模式。适配只在节点/桥各自唯一协议入口扩展；不让启动器直接实现第二套 TLS 身份、分配规则或房间恢复流程。

引入版本能力协商，明确 legacy 与 managed 能力。旧桥仍可按已有节点协议联机；需要中心分配票据的新路径只对相应版本开放，不能拿旧邀请码假装已完成新授权。客户端从控制中心接收少量合适入口，加入房间仍固定到 owner/epoch；旧版单一“当前节点”的状态需拆成控制入口、发现入口和房间路径。

迁移账号时保留原 ID 和用户公钥，验证原发行签名、用户签名和复制策略；对同名账号保留候选。不自动复制私钥、明文密码和超出授权范围的身份密文。旧节点作为来源暂时不可达时明确恢复路径，不伪造成功。

区域策略先在影子模式计算建议但不改变玩家路径，比较现有选择与新候选的 RTT/利用率。随后对新建房间灰度；已有房间保持原归属直到结束。没有数据面状态复制时，不对正在游玩的会话做无提示强制换节点。

## 原型现状

相邻节点项目中的 Python 原型已经验证了中心协调、持久社交投递和故障隔离的若干行为。本次在独立环境获得 Windows 96 项、Linux 51 项、兼容套件 27 项通过；另一个新增备用入口用例独立通过（4.296 秒），不重复计入此前套件。它们属于原型行为测试，不代表 C++ 新项目已实现或达成任何吞吐目标。

原型默认配置仍为 mesh，未替换生产节点。原型短期凭证和共享联邦密钥的设计不符合最新长期公共接入边界，不能直接发布给第三方。详见[原型验收记录](../../minecraft-tunnel-native/docs/40-历史回归/03-20261110-控制中心与故障隔离.md)；源码保留待审，不新增到新项目运行依赖。

## 发布与回退

每次发布同时记录控制协议版本、节点/桥/SDK 版本、数据库迁移和配置版本。数据库迁移先采用可向前兼容的增加字段/表策略，避免灰度期间双版本互相破坏。原有节点/账号数据做一致性备份并实际恢复演练；备份可恢复不等于服务自动高可用。

切换失败时停止新流量进入新路径，撤销未消费预留，保持既有房间到结束，再恢复旧入口。新控制身份不得被旧全网共享密钥替代。生产升级和重启必须有可审阅的版本、配置、验收与回退产物，不能用开发机器回环通过作为上线确认。
